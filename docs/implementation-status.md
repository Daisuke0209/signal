## 検証の根拠

- 全UIを一時的にまとめた `codex/integrated-preview` で、フロントエンド60テスト、lint、本番buildが成功。これはローカル統合検証で、未マージUIをmainへ出したことは意味しない。
- 同じ統合コードでバックエンド129テスト、Ruff、strict mypyが成功。再解析の追加テスト取り込み後は資料APIの24テストも成功した。
- 専用DBでmigration後の `alembic check` が差分なし。CIにも同じ検査を追加し、モデルとDBの型のずれを検出する。
- 実OpenAI APIと架空PDFを使い、SSOの対応プランを根拠ページ付きで提案できた。生成完了まで6.67秒で、2〜5秒の目標達成とは扱わない。ブラウザ描画までの時間でもない。
- 実OpenAI APIで架空の3発言から会議後要約を生成し、完了確認まで4.11秒。見積り送付の約束と契約未決定を区別できた。単一例であり、実商談の品質保証ではない。
- 合成音声を使ったプロバイダー接続と、実際のMeet＋物理マイクを使う端末全体の確認は別物。後者は未確認。

## 学習のために押さえる境界

| テーマ | 今の選択と理由 | 代替・拡張の判断点 |
| --- | --- | --- |
| フルスタックと認可 | FastAPIを業務と権限の境界、Next.jsを表示と入力の境界にする。DBセッションで失効を説明できる | マネージド認証を選ぶ場合も組織認可はAPI側に残す |
| エージェントと検索 | 一つの調査エージェントが限定ツールを使い、起動・上限・保存は決定的な制御で管理 | 日本語検索の評価が不足する場合にハイブリッド検索を検討。専門エージェント分割は必要性を測ってから |
| 状態管理 | 暫定文字起こしはUI、確定発言と生成状態はDB。世代番号・attemptと画面の取消処理で古い結果を拒否 | プロセス増設には共有キューとリースが必要 |
| 副作用と引継ぎ | 承認要求を保存し、人の承認後にアプリ内依頼を一度だけ作る。担当者の受領・回答まで実装 | 外部メール/CRM送信は未実装。追加時も認可と承認境界を維持 |
| 失敗と観測 | 固定エラー、再試行、再起動時の中断回収、IDによるログ相関 | 永続トレース保管やOpenTelemetry導入は運用上の必要に応じて追加 |

現在のバックグラウンド実行は単一APIプロセス向けで、分散永続キューではない。複数プロセス起動をそのまま本番構成にしない。
PDF検索は文字抽出可能な資料を対象とし、OCRは未対応。長大な会議の要約は上限で拒否し、黙って途中を切り捨てない。
APIキーはサーバーの無視対象 `.env` にのみ置く。ログ、Issue、PR、画像には含めない。

## ロック解除後の受け入れ手順

1. 最新UIの統合画面で資料選択、PDF根拠のページ、再解析、承認、担当者の受信/回答、履歴/要約を確認し、各Issueへスクショを掲載する。
2. 最終HEADのレビューとCIを確認してUI PRを依存順にマージし、マージ済みの作業ブランチを削除する。未コミットの別作業は保持する。
3. Mac Chromeで実際のMeetタブと物理マイクを選び、双方の暫定表示と確定保存、提案更新、再読込・商談終了を確認する。
4. 共有停止、切断、セッション失効と再試行を試す。実測サンプル数と環境を記録し、`evaluate_traces` で遅延を確認する。未測定を成功と扱わない。
