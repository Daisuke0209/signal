# 実装と検証の現在地

2026-09-06 追加改善時点。コードの存在、テスト成功、実機での利用確認を区別する。
GitHub の最新 Issue/PR がこの記録より進んでいる場合は、そちらを正とする。

## 機能の状態

| 機能 | 実装・自動検証 | 残る確認 |
| --- | --- | --- |
| 認証・組織認可 | DBセッション、ログイン/ログアウト、組織を跨ぐ商談・資料・承認・引継ぎアクセス拒否を検証 | 実利用者による操作確認 |
| 商談と文字起こし | 作成/復元/終了、Meetタブとマイクの別取得、Realtime中継、確定発言の重複抑止・保存、停止時flushを実装 | 実際のMeet、物理マイク、共有権限、回り込み、切断復旧 |
| 自動提案と資料検索 | 確定発言で起動、選択PDFへの検索/ページ取得、根拠検証、生成状態保存、SSE更新を実装 | 実商談の品質、連続会話での遅延（#102） |
| 資料管理 | 登録/抽出/一覧、認可済み原本表示、失敗からの再解析を実画面で確認・画像掲載済み | 実利用する資料での検索品質 |
| 承認・人への引継ぎ | 承認要求/判断、二重実行抑止、受領/回答、組織境界を検証。実画面で承認→受領→回答→元商談の表示を確認 | 別ユーザー間の権限は自動テストで確認。実利用者による往復は未確認 |
| 履歴・会議後要約 | 終了商談のみ生成、保存/復元、重複開始抑止、失敗再試行、古い処理の破棄を検証 | 実商談の要約品質（履歴UIと保存済み要約の復元は実画面確認済み） |
| ログ・トレース | HTTP相関ID、提案/文字起こし/承認/引継ぎのIDと固定結果、本文非記録を検証 | 実通話のサンプル収集と遅延評価 |

## 音声入力確認後の改善（#105–#109）

- 文字起こしは末尾付近で新しい発言を追従する。過去の発言を読むために上へスクロールした場合は位置を維持し、「最新へ」で追従に戻る。
- 返答例は対応する顧客の実発言を上に表示する。別商談や未来の発言を参照できず、対応が不明な場合は明示する。
- 確認事項は商談ごとにDBへ蓄積し、提案が更新されても消えない。会話の発言を根拠に自動で確認済みにし、根拠の本文を表示する。手動訂正は自動判定より優先する。
- 「次に聞くこと」は確認事項に統合した。未確認の項目を上に、確認済みの項目を下に表示する。

利用者から音声入力の動作成功報告を受けた。Meet固有の共有権限、双方の音声、切断復旧と実測遅延まで確認済みとは扱わず、#102で追跡する。
自動チェックは同じ商談の発言IDをサーバーで検証するが、発言が項目を満たすかの判定はモデルによる。誤判定に備えて根拠表示と手動訂正を用意した。

UIのある #46 / #38 / #39 / #47 / #43 / #75 は、架空データを使った実アプリのスクショを各Issueへ掲載済み。
コミットSHA付き画像URLなので、作業ブランチ削除後も参照できる。画面のコードと証跡を最終レビューしてからマージする。
実際のMeetと物理マイクを使う受け入れ確認は [Issue #102](https://github.com/Daisuke0209/signal/issues/102) に分け、未完了として追跡する。

## 検証の根拠

- 追加改善の統合コードでフロントエンド74テスト、lint、本番buildが成功。バックエンドは #118 の最終headと差分がなく、同PRで145テスト・Ruff・mypy・CIが成功した。統合後のローカルDBも `alembic check` で差分なし。
- #117 で返答対象と自動チェックの統合回帰を修正した。架空データの実API smokeで、既存の確認事項に対する根拠発言IDと、返答対象の顧客発言IDが両方返ることを確認した。
- 全UIをまとめた `codex/integrated-preview-final` で、フロントエンド62テスト、lint、本番buildが成功。最終の日本語エラー表示とボタン整形もこの画面で検証した。
- 同じ統合コードでバックエンド136テスト、Ruff、strict mypyが成功。
- 専用DBでmigration後の `alembic check` が差分なし。CIにも同じ検査を追加し、モデルとDBの型のずれを検出する。
- 実OpenAI APIと架空PDFを使い、SSOの対応プランを根拠ページ付きで提案できた。生成完了まで6.67秒で、2〜5秒の目標達成とは扱わない。ブラウザ描画までの時間でもない。
- 実OpenAI APIで架空の3発言から会議後要約を生成し、完了確認まで4.11秒。見積り送付の約束と契約未決定を区別できた。単一例であり、実商談の品質保証ではない。
- 実画面で資料選択を保存し、再読込後の復元と選択変更に伴う実API自動提案の更新を確認。根拠PDFの1ページ目が原本ビューアに表示され、対応プランと人数条件を確認できた。
- 架空PDFの原本欠損による失敗、日本語エラー、原本を復旧してから再解析で利用可能に戻る流れを実画面で確認。これは欠損原本自体を自動復元する機能ではない。
- 架空商談で承認依頼作成→承認→受信箱→受領→回答→元商談での回答表示を確認。今回はDemo Userが受付役を兼ねた。別担当者の回答拒否・競合・別組織拒否は自動テストで確認した。
- 合成音声を使ったプロバイダー接続と、実際のMeet＋物理マイクを使う端末全体の確認は別物。後者は未確認。

## 学習のために押さえる境界

| テーマ | 今の選択と理由 | 代替・拡張の判断点 |
| --- | --- | --- |
| フルスタックと認可 | FastAPIを業務と権限の境界、Next.jsを表示と入力の境界にする。DBセッションで失効を説明できる | マネージド認証を選ぶ場合も組織認可はAPI側に残す |
| エージェントと検索 | 一つの調査エージェントが限定ツールを使い、起動・上限・保存は決定的な制御で管理 | 日本語検索の評価が不足する場合にハイブリッド検索を検討。専門エージェント分割は必要性を測ってから |
| 状態管理 | 暫定文字起こしはUI、確定発言と生成状態はDB。世代番号・attemptと画面の取消処理で古い結果を拒否 | プロセス増設には共有キューとリースが必要 |
| 副作用と引継ぎ | 承認要求を保存し、人の承認後にアプリ内依頼を一度だけ作る。担当者の受領・回答まで実装 | 外部メール/CRM送信は未実装。追加時も認可と承認境界を維持 |
| 失敗と観測 | 固定エラー、再試行、再起動時の中断回収、IDによるログ相関 | 永続トレース保管やOpenTelemetry導入は運用上の必要に応じて追加 |

現在のバックグラウンド実行は単一APIプロセス向けで、分散永続キューではない。複数プロセス起動をそのまま本番構成にしない。
現在の承認依頼は人が入力して作成する。AIが操作を提案して承認要求を作る経路は未接続。
PDF検索は文字抽出可能な資料を対象とし、OCRは未対応。長大な会議の要約は上限で拒否し、黙って途中を切り捨てない。
APIキーはサーバーの無視対象 `.env` にのみ置く。ログ、Issue、PR、画像には含めない。

## 残る実端末の受け入れ手順

1. Mac ChromeでSignalと実際のMeetを開き、利用者がMeet共有タブの音声と物理マイクを選ぶ。
2. 相手と自分が架空の商談内容を発話し、双方の暫定表示、確定保存、自動提案、根拠表示、再読込後の復元を確認する。
3. 共有停止、マイク切断、接続失敗、セッション失効と再試行を試す。最後に商談を終了し、未保存発言が失われていないか確認する。
4. Chrome/macOS、音声ソース、モデル、サンプル数と実測値をIssue #102へ記録する。`evaluate_traces` で遅延を確認し、目標未達と未測定を成功扱いにしない。

利用者のMeetタブ選択・物理マイクでの発話が必要なので、自動テストだけでこの項目を閉じない。発見した実装不備は小さな修正Issueに分ける。
