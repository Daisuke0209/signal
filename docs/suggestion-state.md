# 提案の生成状態と保存境界

Issue #33では、生成実行を `suggestion_runs`、表示する提案を `suggestions` に分けて保存する。
1つの実行が複数の質問・返答例・確認事項を返すため、実行の状態と表示内容を別に扱う。
JSONを会話テーブルに上書きする方法よりテーブルは増えるが、失敗・再試行・入力時点を説明できる。

生成開始時に会話行をロックし、最新の確定発言番号と会話内の生成番号を記録する。
生成番号は同時開始でも重複せず、会話と入力発言番号の複合外部キーで別会話や未保存の発言を参照できない。
この短いトランザクションをcommitしてから外部AIに接続する。生成中に会話行をロックし続けない。

状態遷移は `queued → running → succeeded` または `queued/running → failed`。
完了した実行は変更せず、再試行時は新しい実行を作る。結果の追加と成功への変更は同じトランザクションで確定する。
失敗理由は固定コードだけを保存・返却し、プロバイダーの例外本文や機密情報を入れない。

`GET /conversations/{conversation_id}/suggestions` は所属組織を確認して最新の実行を返す。
生成番号で選び、完了時刻では選ばない。古い実行が後から成功しても新しい実行を上書きしない。
提案がまだない場合は `latest_run: null`。最新実行が待機・実行中・失敗なら、その状態と空の結果を返す。
成功した実行は不変なので、読み取り時の2つのSQLの間に生成が終わっても、実行中の表示に結果だけ混ざらない。

生成開始・実行・成功・失敗のPython関数は内部サービス向けで、HTTPの書き込みAPIとして公開しない。
呼び出すイベント/API境界が認証と認可を行い、各関数の呼び出し後は呼び出し側がcommit/rollbackする。
提案の自動生成、外部AIへの接続、資料の根拠、起動時の中断実行の回復は #34 で接続する。
本Issueの取得APIは状態を保存・復元する基盤であり、まだ自動提案を起動しない。

検証は実PostgreSQLとHTTPで、3種類の結果の復元、遅い旧結果、失敗後の変更拒否、並行開始、
組織境界、入力発言の外部キー、結果保存失敗時の原子性、空/終了会話の開始拒否を確認する。

参照: [SQLAlchemyの複合外部キー](https://docs.sqlalchemy.org/en/20/core/constraints.html#defining-foreign-keys)
